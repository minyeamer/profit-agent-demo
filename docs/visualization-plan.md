# 분석 에이전트 구현 로드맵

## 문서 목적

자연어 실적 분석 데모를 단순한 결과 표 조회 화면에서, **근거를 확인하고 추이를 비교하며 결과를 재현할 수 있는 분석 도구**로 발전시키기 위한 전체 구현 계획이다.

이 문서는 최초 1순위였던 그래프 기능뿐 아니라, 앞선 논의에서 제안한 후속 개선 항목을 우선순위·범위·검증 기준과 함께 관리한다.

## 공통 설계 원칙

1. 모델은 제공된 read-only 분석 도구만 선택한다. 임의 SQL·Python·차트 사양을 생성하거나 실행하지 않는다.
2. 애플리케이션은 구조화된 도구 결과를 단일 데이터 원천으로 사용한다.
3. 숫자·기간·필터·집계 기준은 모델의 자연어 답변이 아니라 도구 결과에서 직접 표시한다.
4. 차트는 표를 대체하지 않는다. 그래프와 원본 집계표를 함께 제공한다.
5. 날짜·차원·지표·집계 방식·행 수는 allowlist와 상한을 유지한다.
6. API 키, DB 연결정보, SQL, 전체 대화 원문은 화면·다운로드·로그에 포함하지 않는다.
7. 데모 데이터의 가용 기간은 `2025-08-01 ~ 2026-07-31`이다. 존재하지 않는 미래 기간을 0 또는 추정값으로 표시하지 않는다.

## 1순위 — 결과 표 + 그래프 시각화

### 목표

분석 도구의 구조화 결과를 Streamlit에서 다음 세 요소로 함께 표시한다.

```text
자연어 질문
  → 허용된 분석 도구 호출
  → 구조화된 분석 결과
  → 자연어 해설 + 분석 조건 + 표 + 그래프
```

### 완료된 구현

- `AgentRunResult`를 도입해 최종 답변과 마지막 성공 도구 결과를 함께 전달한다.
- 도구 결과를 대화 기록에 보존해 이전 답변의 표·그래프를 다시 렌더링한다.
- 월별 추이 조회가 하나의 추가 집계 기준을 지원한다.
  - 예: `grain="month"`, `group_by=["brand_name"]`
- 월별·브랜드별 결제금액을 브랜드별 다중 선 그래프로 표시한다.
- 기간 전체 결제금액 상위 상품을 안전하게 선정한 뒤, 해당 상품들의 일별 결제금액을 한 번의 allowlist 조회로 반환한다.
- 상품뿐 아니라 브랜드·쇼핑몰 그룹(`shop_group`)·판매처(`shop_name`)·담당팀·카테고리 등 허용된 차원에 대해 동일한 상위 N 일별 추이 계약을 사용한다.
  - 한국어·영어 별칭은 semantic schema와 시스템 매핑 규칙으로 canonical column에 매핑한다.
  - 예: 쇼핑몰/mall → `shop_group`, 판매처/shop/seller/channel → `shop_name`.
  - `get_top_product_trend(start_date, end_date, limit=10)`
  - 최대 20개 계열, 최대 366일, 최대 1,000행으로 제한한다.
  - 상품 선정 기준과 일별 추이는 동일 기간·동일 필터를 사용한다.
- 서비스가 반환한 검증된 `chart` 계약(`kind`, `title`, `x_column`, `series_column`, `value_column`)을 Streamlit이 결정적으로 해석한다.
  - 모델이 JSON 차트 정의를 작성하거나 실행하지 않는다.
  - 현재 지원 범위는 `period`/`order_date` 시간축의 다중 선 그래프다.
- 차트 계약이 있는 조회는 두 번째 모델 해설 호출 없이 즉시 표·그래프를 표시한다.
  - 불필요한 JSON·텍스트 기반 그래프 설명을 화면에 표시하지 않는다.
- 분석 단계는 `분석 요청 해석 → 안전한 데이터 조회 → 그래프 준비/응답 정리 → 결과 표시` 상태 패널로 표시한다.
- API 클라이언트의 각 호출은 90초 timeout과 재시도 없음으로 제한한다.
- 그래프와 함께 원본 표를 표시한다.
- 기간·집계 기준·지표·필터를 화면에 표시한다.
- 전 기간 결제금액이 0인 계열은 그래프에서 제외하고, 원본 표에는 보존한다.
- Streamlit의 중단 예정 인자를 `width="stretch"`로 교체했다.

### 첫 번째 기능 검증 질문

```text
2026년 월별 브랜드별 결제금액 변화를 집계하여 비교해 주세요.
```

기대 결과:

- 시간 축: `2026-01-01 ~ 2026-07-01`
- 계열: 결제금액이 존재하는 브랜드
- 원본 집계 결과: 2026년 1월~7월 월별·브랜드별 행
- 그래프: 브랜드별 선 5개, 월 7개
- 미래 8~12월은 표시하지 않음

### 후속 차트 유형

| 구조화 결과 | 표시 방식 |
|---|---|
| `get_profit_trend` + 시간축 + 브랜드/채널 1개 차원 | 다중 선 그래프 |
| 비시간 차원 1개 + 지표 1개 | 막대 그래프 |
| `get_top_products` | 대표상품 상위 20개 가로 막대 그래프 |
| 조건 불충족·빈 결과·과도한 범주 | 표와 분석 조건만 표시 |

### 검증 기준

- 차트 사양 생성 순수 함수 테스트
- 월별·브랜드별 피벗 데이터 테스트
- 빈 결과·단일 행·날짜 오류·전부 0인 계열 테스트
- 실제 데모 DB에서 `7개월 × 5브랜드` 입력 검증
- Streamlit 브라우저에서 선 그래프와 표 동시 표시 확인

## 2순위 — 직전 기간 비교와 KPI 카드

### 목표

특정 기간의 절대값뿐 아니라 직전 동일 기간과 비교해 실적 변화의 의미를 바로 보여준다.

### 구현 범위

새 구조화 도구를 추가하거나 기존 추이 도구를 확장한다.

```text
get_profit_comparison(
  start_date,
  end_date,
  compare_to="previous_period",
  group_by,
  metrics,
  filters
)
```

표시 항목:

- 현재 기간 결제금액·영업이익·영업이익률
- 직전 동일 기간 값
- 증감액·증감률
- 브랜드별 상승·하락 순위
- 결제금액은 증가했지만 영업이익은 감소한 그룹

### 주의사항

- 비교 기간은 현재 기간과 동일한 일수로 계산한다.
- 분모가 0인 증감률은 `0%`로 위장하지 않고 `—` 또는 `계산 불가`로 표시한다.
- 기간 경계와 포함 범위를 테스트한다.

### 완료 기준

- KPI 카드가 표와 같은 집계 결과를 사용한다.
- 직전 기간·증감액·증감률이 자동 테스트로 검증된다.
- 브랜드별 상승·하락 그래프가 동일한 비교 결과에서 렌더링된다.

## 3순위 — 분석 근거와 재현성 강화

### 목표

모델의 설명이 흔들리더라도 사용자가 어떤 데이터를 기준으로 답변이 만들어졌는지 확인할 수 있게 한다.

### 구현 범위

모든 분석 결과에 다음 메타데이터 카드를 표시한다.

```text
조회 기간
집계 기준
지표
필터
주문상태 포함 범위
결과 행 수
```

추가 개선:

- 모델 답변이 비어 있는 집계 기준을 작성하지 못하도록 애플리케이션이 직접 채운다.
- 모델 답변의 수치와 원본 표의 수치를 검증할 수 있는 결과 요약을 제공한다.
- 분석 조건을 JSON 또는 안전한 query state로 저장한다.
- 동일 조건을 다시 실행할 수 있는 재현 링크를 검토한다.

### 완료 기준

- 분석 조건은 모델 응답이 아니라 구조화 결과에서 표시된다.
- SQL·API 키·연결정보가 재현 링크에 포함되지 않는다.
- 동일 조건을 다시 실행했을 때 동일한 구조화 결과를 얻는 테스트가 있다.

## 4순위 — 결과 CSV 다운로드

### 목표

그래프를 확인한 뒤 사용자가 안전한 집계 결과를 별도로 내려받을 수 있게 한다.

### 구현 범위

- 원본 집계 행 CSV 다운로드
- UTF-8 인코딩 및 한국어 호환
- 기간·도구명을 포함한 결정적 파일명
- 차트에 표시한 데이터와 다운로드 데이터의 일치 보장

예시 파일명:

```text
profit-analysis_2026-01-01_2026-07-31_get_profit_trend.csv
```

### 금지 항목

- SQL 문장
- DB 연결정보
- API 키
- 전체 대화 전문
- 내부 실행 로그

### 완료 기준

- 화면 표와 CSV의 행 수·컬럼·값이 일치한다.
- 빈 결과도 정상적인 헤더 CSV로 다운로드된다.
- 다운로드 내용에 비공개 설정값이 없는지 테스트한다.

## 5순위 — API 운영 안정성과 비용 관측

### 목표

제공자와 모델을 바꾸더라도 장애 원인과 비용 영향을 확인할 수 있게 한다.

### 구현 범위

비밀값과 사용자 데이터가 없는 범위에서 다음 메타데이터를 기록하거나 개발자 화면에 표시한다.

- 제공자와 모델
- API 요청 지연 시간
- 도구 호출 횟수
- 성공·실패 유형
- rate limit 재시도 횟수
- API 응답이 제공하는 토큰 사용량

### 안정성 보완

- API 요청 timeout 설정
- 404, 401, 403, 429, 5xx를 서로 다른 사용자 메시지로 구분
- 429 외 오류는 무분별하게 재시도하지 않음
- 제공자별 모델·tool calling 지원 여부를 capability로 관리
- 긴 응답과 도구 결과의 크기 상한 유지

### 완료 기준

- API 키와 전체 프롬프트가 로그에 남지 않는다.
- 404는 endpoint·model 설정 문제로 안내한다.
- 인증 오류와 rate limit 오류를 구분한다.
- 성공·실패·재시도 동작이 mock 테스트로 검증된다.

## 6순위 — 대화 문맥과 사용자 경험 관리

### 목표

대화가 길어져도 비용·응답 지연·컨텍스트 오류가 과도하게 증가하지 않도록 한다.

### 구현 범위

- 최근 대화 N개 또는 토큰 상한 설정
- 오래된 도구 결과의 전문을 무제한으로 API에 재전송하지 않음
- 대화 초기화 기능 유지
- 분석 결과 카드와 자연어 답변을 시각적으로 구분
- 로딩 중 요청 취소 또는 중복 제출 방지
- 오류 후 재시도 버튼과 설정 확인 안내

### 완료 기준

- 메시지 상한을 넘었을 때 오래된 메시지를 안전하게 축약·제거한다.
- 도구 결과가 중복으로 전송되지 않는다.
- 새 대화와 이전 결과 표시가 분리된다.

---

## 7순위 — 보안·데이터 품질 보완

### 구현 범위

- 모든 추이 쿼리가 relation·날짜·차원·필터 allowlist를 공통으로 사용
- SQL 식별자는 allowlist에서만 생성
- 날짜 범위 최대 366일 유지
- 결과 최대 1,000행 유지
- 그래프 범주 최대 20개, 상품 순위 최대 20개 유지
- read-only transaction과 statement timeout 유지
- `브랜드 없음`·빈 차원값을 표와 그래프에서 일관되게 처리
- 비정상적으로 큰 값·음수 이익·0분모 지표 표시 규칙 추가
- 공개 데이터에 실제 내부 행·상품명·식별자·연결정보가 포함되지 않았는지 검사

### 완료 기준

- 모든 신규 쿼리 빌더에 injection·long-range·unknown-dimension 테스트가 있다.
- 차트가 임의 컬럼이나 임의 코드를 실행하지 않는다.
- 공개 파일의 비밀값·연결 URI·개인정보 패턴 검사가 통과한다.

## 8순위 — CI와 회귀 검증

### 목표

로컬에서만 통과하는 데모가 되지 않도록 공개 저장소의 변경을 자동 검증한다.

### CI 단계

```text
1. 의존성 설치
2. pytest
3. Python compileall
4. shell syntax check
5. Docker Compose config check
6. git diff --check
7. 공개 파일 비밀값·연결정보 검사
```

외부 API는 CI에서 실호출하지 않고 mock으로 검증한다. 실제 API smoke test는 로컬 수동 절차로만 유지한다.

### 완료 기준

- 모든 Pull Request에서 핵심 테스트가 실행된다.
- 실제 credential이 CI 로그에 출력되지 않는다.
- 테스트 실패 시 차트·쿼리·API 설정 영역을 구분할 수 있다.

## 권장 실행 순서

```text
완료: 1순위 결과 표 + 월별 브랜드 선 그래프
  ↓
2순위 직전 기간 비교 + KPI 카드
  ↓
3순위 분석 근거·재현성
  ↓
4순위 CSV 다운로드
  ↓
5순위 API 오류·지연·비용 관측
  ↓
6순위 대화 문맥·UX 관리
  ↓
7순위 보안·데이터 품질 보완
  ↓
8순위 CI·자동 회귀 검증
```

각 순위는 반드시 다음 순서로 구현한다.

```text
실패 테스트 작성
→ 실패 확인
→ 최소 구현
→ 관련 테스트 통과
→ 전체 회귀 검증
→ 문서 상태 갱신
```
